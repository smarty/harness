Type-Scoped Recovery

Scope the startup recovery backlog to the message types registered at wireup time.

2026-07-09 · branch mikewhat/scoped-recovery · status: IMPLEMENTED — all checklist items complete (2026-07-09)

Background

At startup, the recovery station republishes every stored-but-undispatched message: adapters.Recovery snapshots MIN(id)/MAX(id) of rows WHERE dispatched IS NULL, then pages that frozen window in id order. Both queries are type-blind — they consider every row in the Messages table.

Meanwhile, the pipeline already knows exactly which message types it owns: Options.MessageTypes(map[reflect.Type]string) supplies the stored type names the execution stage stamps onto every message it produces (internal/pipeline/01_execution.go:70). Nothing this pipeline instance writes can carry a type name outside that map's values.

Type-blind recovery misbehaves whenever the Messages table contains rows this instance did not write and does not own:

  • Shared tables. If another application (or an older revision of this one) leaves undispatched rows of foreign types, this instance republishes them through its dispatcher — messages it never agreed to own, possibly to the wrong exchange, possibly types its consumers cannot parse.
  • Poisoned windows. A single ancient undispatched foreign row pins MIN(id) near zero, so every page query scans an enormous dead prefix. A foreign row also flips Found to true when this instance's own backlog is actually empty, forcing pointless page queries before live traffic is served — and recovery stalls the whole pipeline by design.
  • Precedent already exists. The snapshot-replay path solved this same problem the same way: LoadEventsSince takes a set of stored type names and queries WHERE type IN (...). Recovery is the last type-blind reader.

Prior sessions established the pieces this builds on: the paged keyset-cursor recovery (2026-06-12 f7-paged-recovery) and routing recovery through the storage.Storage seam (2026-06-16 recovery-storage-db-routing).

Approach

Thread the configured type names from Configuration.MessageTypes down to the two recovery SQL queries. Four small changes along one existing seam — no new options, no schema change, no new interfaces.

1. Operation contracts — internal/storage/operations.go

Both recovery operations gain a Types field. Documented semantics: a non-empty slice scopes the query to those stored type names; an empty slice means unscoped (today's behavior).

// LoadUndispatchedBounds reports the id range of the undispatched backlog,
// optionally scoped to the given stored type names (empty Types = all types).
type LoadUndispatchedBounds struct {
    Types []string // sorted stored type names to scope to; empty = unscoped
    Found bool
    Min   uint64
    Max   uint64
}

// LoadUndispatchedPage loads up to Limit undispatched messages in id order
// within the half-open window (AfterID, ThroughID], optionally scoped to the
// given stored type names (empty Types = all types).
type LoadUndispatchedPage struct {
    Types     []string
    AfterID   uint64
    ThroughID uint64
    Limit     int
    Messages  []*contracts.Message
}

Decision: []string, not map[string]struct{}

LoadEventsSince uses a set and re-sorts it inside the Mapper on every call. Recovery issues the page query repeatedly while draining a large backlog, and the scope never changes after wireup — so the adapter sorts and dedupes once in its constructor and hands the Mapper a stable, ready-to-bind slice. Deterministic argument order also makes assertions trivial. (Happy to switch to the set form for consistency if you prefer.)

2. Adapter — internal/adapters/recovery.go

func NewRecovery(db storage.Storage, types []string) *Recovery {
    return &Recovery{db: db, types: slices.Compact(slices.Sorted(slices.Values(types)))}
}

snapshot and page set op.Types = this.types on the ops they already build. The cursor logic is untouched: bounds and pages both see the same filtered universe, so the frozen-window invariants (advance only after a clean page, empty page = done) hold exactly as before, just over a smaller set of rows.

3. Wiring — internal/pipeline/pipeline.go

newRecovery(ctx,
    adapters.NewRecovery(config.Storage, messageTypeNames(config.MessageTypes)),
    recoveryBatchSize, work4a, wait, config.Monitor),

where messageTypeNames is a small helper returning the map's values (the stored names), sorted and deduplicated — duplicates are possible since two Go types may legitimately share a stored name.

4. SQL — storage/mysql/mapper.go

Both queries append AND type IN (?, …) when len(op.Types) > 0. Because the IN-list makes the SQL dynamic, both methods move onto the pooled statement builder already used by markMessagesDispatched and loadEventsSince:

SELECT MIN(id), MAX(id)              SELECT id, type, payload
  FROM `Messages`                      FROM `Messages`
 WHERE dispatched IS NULL             WHERE dispatched IS NULL
   AND type IN (?, ?)                   AND type IN (?, ?)
                                        AND id > ? AND id <= ?
                                      ORDER BY id
                                      LIMIT ?

Page-loop termination stays correct under filtering: LIMIT counts matching rows, the cursor advances to the last returned id, and an empty page still means no matching rows remain in the window.

Decision: empty MessageTypes ⇒ unscoped recovery (backward compatible)

When no MessageTypes are configured, recovery behaves exactly as today. Rationale: (a) inert/test pipelines built with zero options keep working; (b) an app that never configured MessageTypes persists rows with type = '' (the map-miss zero value), and unscoped recovery still picks those up. The strict alternative — scoping to the literal empty-string type — punishes legacy configs for no safety gain, and the sharp alternative — failing validation when MessageTypes is empty — would break every existing minimal wireup. Scoping is therefore effectively opt-in via the option production apps already set.

Trade-offs & Open Questions

⚠ Behavior change: rows outside the scope become invisible to recovery

Once deployed with MessageTypes configured, undispatched rows whose stored type is not in the configured set are never republished by this instance — including rows written as type = '' by a pre-MessageTypes deployment, rows from a since-renamed type, and rows produced by a domain value missing from the map. That is the point of the feature, but it converts "eventually recovered" into "sits undispatched forever." Deployment note: before rolling out, confirm the configured names cover every type the app has ever written that could still be undispatched (or drain the backlog first).

ConcernAssessment
Index support ix_messages_dispatched (dispatched, id) does not cover type, so the type filter is applied after the index narrows to undispatched rows. Worst case, a page scans a window full of foreign-type rows. Recovery is startup-only and the backlog is normally small, so I propose no schema change now; if a shared-table deployment ever hurts, an index on (dispatched, type, id) is a follow-up.
Unmapped produced values The execution stage still stamps type = '' for values absent from MessageTypes, and those rows will now never recover. Validating "every value a handler can produce has a name" statically is impossible (handlers emit any); out of scope here, worth a future guard in the serialization stage if desired.
IN-list size Type counts are small (tens, not thousands); no statement-length or plan-cache concern. Sorted names keep the generated SQL text identical across calls.
Inconsistency with LoadEventsSince That op takes map[string]struct{} and errors on empty; the recovery ops take []string and treat empty as unscoped. The differing empty-semantics are deliberate (replay without registered events is a programming error; recovery without MessageTypes is a supported legacy config) and will be documented on the op structs. Unifying the collection types is possible follow-up polish, not part of this change.

Out of Scope

  • Schema changes (the optional (dispatched, type, id) index).
  • Guarding against produced values missing from MessageTypes (rows stamped type = '').
  • Unifying the Types collection shape with LoadEventsSince.
  • Scoping MarkMessagesDispatched or any write path — writes are already inherently scoped to what this instance produced.
